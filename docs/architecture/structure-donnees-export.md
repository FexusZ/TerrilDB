# Édition de structure, export, édition de données

Détail déplacé de `CLAUDE.md` sans modification de fond ; les règles essentielles restent dans `CLAUDE.md`.

## Édition de structure (src/Core/Schema/Change, TableStructureController)

Modifier colonnes, index, clé primaire, clés étrangères, nom ou suppression d'une table SQL. Le client n'envoie JAMAIS de SQL : il envoie
la table telle qu'on la veut (`TableDraft` : chaque colonne, index ou clé étrangère garde son `originalName`, ce qui reconnaît un
renommage) ; le serveur relit la table réelle, `SchemaDiffer` déduit les opérations, un `DdlDialect` par moteur (PostgreSQL, MySQL +
MariaDB, ClickHouse) les écrit, `SchemaChangePlanner` rend le `ChangePlan` (instructions ordonnées : on retire d'abord clés
étrangères, index, clé primaire puis colonnes, on remet ensuite clé primaire, index, clés étrangères, le renommage de la table vient
en dernier). Le texte libre est borné : `ColumnType::validated` n'accepte que la FORME d'un type (mots, nombres, chaînes fermées,
parenthèses équilibrées, aucun mot de contrainte), `DefaultValue::parse` lit NULL, un nombre, une chaîne ou une courte liste
d'expressions (now(), uuid(), true…) et traite tout le reste comme une CHAÎNE échappée, jamais comme du SQL ; les noms passent par
`NameRule` puis sont échappés par le dialecte. Deux routes : `POST /web/connections/{id}/tables/{name}/structure/preview` (n'écrit rien :
instructions, `transactional`, `destructive`, `stale`) et `.../apply` (`fingerprint` obligatoire : empreinte de la structure rendue par la
lecture de la table, 409 `schema_changed` si la table a bougé entre-temps ; 409 `confirmation_required` + liste tant que `confirmed` manque
pour ce qui détruit : retirer colonne, index, clé, changer un type, supprimer la table ; 409 `schema_change_failed` avec `applied` et
`failed` ; 422 `invalid_schema_change`). `drop: true` à la place de `draft` supprime la table. Exécution par `TargetConnection::ddl()`
(`DbalDdlExecutor`, `ClickHouseDdlExecutor`) : PostgreSQL en UNE transaction (tout ou rien, `lock_timeout` 10 s), MySQL/MariaDB et
ClickHouse instruction par instruction (un échec laisse les précédentes appliquées, rapportées dans `applied`). Audit `schema.changed` /
`schema.failed` avec le SQL exact. Défauts : MariaDB rend `current_timestamp()`, `curdate()` et des chaînes entre apostrophes, MySQL `CURRENT_TIMESTAMP` : `DefaultValue` ramène les deux à la même expression canonique (sans parenthèses vides) ; une expression de défaut entre parenthèses (`(1 + 1)`, rendue par les deux familles) non touchée est redite telle que le moteur la rend à `MODIFY COLUMN` (`MySqlDdlDialect::isParenthesised`), jamais lue depuis un texte tapé. Tests : `tests/Integration/Driver/MySqlFamilyDifferencesTest` (4 cibles). Particularités : MySQL `MODIFY COLUMN` redit la définition (commentaire gardé, jeu de caractères
remis à celui de la table), colonne AUTO_INCREMENT nouvelle et sa clé dans un seul ALTER ; ClickHouse : nullabilité dans le type,
clé de tri en lecture seule, ni clé primaire ni clé étrangère ni auto-incrément ni renommage d'index, index de saut matérialisés ;
passer de Nullable à non-Nullable y exige une valeur par défaut. Seules les tables sont éditables (pas les vues), pas Redis.
Front : `TableEditor` (colonnes, index, clés étrangères modifiables sur place ; brouillon `utils/structureDraft` où colonnes, clé primaire, index et clés étrangères se réfèrent par identifiant donc un renommage les suit ; lignes nouvelle / modifiée / retirée surlignées ; barre collante en haut avec le SQL calculé par `preview`, boutons Valider / Annuler, confirmation qui liste ce qui sera perdu ; « Supprimer la table » avec le SQL montré), seulement pour les tables (une vue reste en lecture seule), la section Index est un tableau façon phpMyAdmin (une ligne par colonne avec son rang, nom / type / unique en cellules fusionnées, monter, descendre, ôter, ajouter une colonne ; la clé primaire en est la première ligne, la clé de tri ClickHouse une ligne verrouillée) ; le menu « Vues de la connexion » garde une entrée « Structure » vers la dernière table ouverte (base et schéma compris) ; `TablePane` rafraîchit les listes de tables et l'arbre après application. Tailles : `IndexDefinition::$sizeBytes` et `TableDefinition::$dataBytes/$indexBytes` (octets sur disque, nuls si le moteur ne les donne pas ; HORS de l'empreinte, ils bougent sans que la structure change) : PostgreSQL `pg_relation_size` / `pg_table_size` / `pg_indexes_size` ; MySQL/MariaDB `information_schema.TABLES` pour les totaux et `mysql.innodb_index_stats` pour les index secondaires (lecture facultative, la clé primaire InnoDB est la table : pas de taille propre) ; ClickHouse `system.parts` (`bytes_on_disk`, `primary_key_size`) et `system.data_skipping_indices`. Le front montre une colonne « Taille » des index et « Données / Index / Total » sous le titre de la table. Fidélité sur les objets avancés, tranche versionnement (#85) : `TableDefinition::$versioned` (MariaDB, `TABLE_TYPE = 'SYSTEM VERSIONED'`, HORS empreinte : une table qui le devient entre-temps est relue à l'application, donc refusée comme telle). Les colonnes de début/fin de ligne IMPLICITES sont cachées par le moteur (ni `COLUMNS`, ni `STATISTICS`) : jamais dans le modèle, donc jamais dans un INSERT/UPDATE de la grille, et le brouillon ne peut pas les nommer. Les colonnes EXPLICITES (`GENERATED ALWAYS AS ROW START/END`, `GENERATION_EXPRESSION` = `ROW START|END`) sont verrouillées `LockReason::SystemPeriod` (pas `Generated`) ; leur fin de ligne est dans la clé primaire (SHOW CREATE `PRIMARY KEY (id, re)`). `SchemaDiffer` refuse (`UnsupportedSchemaChangeException`, 422 `unsupported_schema_change`, `reason: system_period`) de renommer ou supprimer une colonne de période ou de la sortir de la clé primaire : DROP SYSTEM VERSIONING n'est jamais généré (le brouillon ne sait pas le dire), et retirer les deux colonnes de période en `system_versioning_alter_history=KEEP` ferait perdre le versionnement explicite. Mesuré : par défaut (`ERROR`) le moteur refuse TOUT ALTER d'une table versionnée (4119, `schema_change_failed` brut) ; en `KEEP` ils passent et l'historique est gardé ; DROP TABLE détruit l'historique. `ChangePlan::$losses` (`PlanLoss`, présenté en `losses: [{code, subject, values}]` par `ChangePlanPresenter`) : `system_history` (suppression d'une table versionnée, listée dans la confirmation qui existait déjà pour tout DROP) et `values_removed` (valeurs retirées d'une liste ENUM/SET, MySQL/MariaDB seulement, `EnumMembers::of` lit la liste ; un retrait avec des lignes qui la portent est refusé par le moteur en mode strict, « Data truncated », ou les perd sans strict : la confirmation le dit). `DataChangePlanner` refuse (422 `invalid_data_change`) une valeur donnée à une colonne `Generated` ou `SystemPeriod` avant l'envoi (une valeur remise telle quelle n'est pas un changement). `SchemaPresenter::table` rend `versioned`. Front : encart « Table versionnée » dans `TableEditor`, `utils/planLoss.lossSentence` dans les deux confirmations. Mesuré et SANS perte (`tests/Integration/Driver/RichTableRoundTripTest`, table riche : colonne générée stockée, index invisible/IGNORED, expression (MySQL), CHECK de table, ENUM, SET, ON UPDATE CURRENT_TIMESTAMP, FULLTEXT, sur MySQL 8.4/26 et MariaDB 11.8/13) : un brouillon identique ne produit AUCUN SQL, renommer/ajouter/retirer colonnes et index ne fait rien perdre ; renommer ou retirer une colonne citée par un CHECK de table est refusé par le moteur (MySQL « Check constraint … uses column … cannot be dropped or renamed », MariaDB 1054 au retrait) ; CHECK n'est pas encore LU dans le modèle. Pas fait : lecture de l'historique (`FOR SYSTEM_TIME`), règle d'audit « historique sans partition SYSTEM_TIME » (dépend de la lecture des partitions, #123). Tests : `tests/Core/Schema/Change/SchemaDifferVersionedTest`, `PlanLossTest`, `tests/Core/Data/DataChangePlannerLockedColumnsTest`, `tests/Integration/Driver/VersionedTableTest`.
Pré-contrôle des verrous (#72, `LockDiagnostics::tableHolders`, `TableHolders`/`TableHolder`) : `preview` rend `lockCheck` (`{status, holders[]}`, nul pour ClickHouse/Redis ou sans instruction), les sessions qui tiennent la table (MySQL : `performance_schema.metadata_locks` accordés + `threads`, âge par `INNODB_TRX` ; PostgreSQL : `pg_locks` relation accordée + `pg_stat_activity`, exige `pg_read_all_stats`) ; session, utilisateur, âge, inactive, mode, JAMAIS le texte de leur requête. AVERTISSEMENT seulement, jamais un blocage ; tout échec de lecture ou source illisible = état (`disabled` : MariaDB sans performance_schema, qui est éteint par défaut ; `permission_denied`) ou `lock_check_failed`, jamais une erreur. Délai dépassé (`lock_wait_timeout` 10 s MySQL/MariaDB 1205, `lock_timeout` PostgreSQL 55P03) : `SchemaChangeFailedException::$lock` (`LockConflict`, lot #73) et `$holders` (relus APRÈS l'échec) ; la réponse porte le code stable `lock_timeout` (ou `deadlock`) avec `retryable`, `applied`, `failed`, `lockTimeout` et `lockCheck` (la lecture des détenteurs n'écrit pas `diagnostic.read` : le cœur n'a pas le contexte d'audit), l'éditeur dit « une transaction ouverte retient cette table » et nomme les sessions. Jamais de KILL. Pas encore : aperçu de l'algorithme INSTANT/INPLACE/COPY. Algorithme probable de chaque instruction (#72, `src/Core/Schema/Change/Algorithm`, LECTURE SEULE : l'aperçu n'essaie JAMAIS d'ALTER) : `AlterAlgorithmAdvisor::advise` rend un `AlgorithmAdvice` par instruction du plan (`ChangePreview::$algorithms`, route `preview` seulement : `algorithm` `instant|inplace|copy|rewrite|unknown`, `blocksWrites`, `copiesTable` (nuls = non vérifié), `estimatedExtraBytes` = données + index pour une copie/réécriture, `algorithmReason` = code stable : `unverified_version`, `not_innodb`, `depends_on_sql_mode`, `unverified_change`, `not_an_alter`, `unsupported_engine` ; champs en plus dans chaque instruction, aucun retiré). Table de règles PURE `AlterAlgorithmRules` (jeu `RuleFamily` = moteur ET série vérifiée : MySQL 8.4 et 26, MariaDB 11.8 et 13, PostgreSQL 18 ; toute autre version ou version illisible, table non InnoDB, Vitess, ClickHouse = `unknown`) ; `TypeChangeClassifier` lit la FORME des types (autre famille de type, signé/non signé, DECIMAL, VARCHAR réduit, ENUM modifié = copie ; membres d'ENUM ajoutés en fin = instantané ; élargir un VARCHAR = inconnu car l'octet de longueur dépend du jeu de caractères). Plusieurs gestes sur une colonne : une copie l'emporte, sinon un inconnu rend le tout inconnu. Chaque règle est VÉRIFIÉE par `tests/Integration/Driver/AlterAlgorithmTest` (l'instruction que le vrai planificateur écrit, rejouée sur une table jetable `tdb_alg_<hex>` avec `ALGORITHM=INSTANT`, `INPLACE` puis `COPY`, refus 1845/1846 = « pas cet algorithme » ; jamais sur `shop`) et `AlterAlgorithmPostgreSqlTest` (fichier `pg_class.relfilenode` avant/après dans une transaction annulée + verrou de `pg_locks`). Constats : instantané = ajout de colonne en fin (types simples, défaut littéral ou `now()`), retrait d'une colonne sans index, renommage d'une colonne non indexée, changement de défaut, renommage de table, membres d'ENUM ajoutés ; en place sans bloquer les écritures (`LOCK=NONE` accepté) = index, clé primaire ajoutée, NOT NULL retiré, et sur MySQL seulement renommage d'index et retrait de clé étrangère (MariaDB : instantané) ; copie = changement de type, clé étrangère ajoutée, clé primaire retirée. MySQL refuse `LOCK=NONE` avec COPY (écriture concurrente mesurée bloquée) ; MariaDB 11.8/13 l'ACCEPTENT et laissent écrire pendant la copie quand le journal binaire est éteint : sa copie n'est donc PAS annoncée comme bloquante (`blocksWrites` nul). NULL vers NOT NULL : MariaDB en place, MySQL inconnu (en place seulement sous un `sql_mode` strict, le test le montre). Renommer une colonne indexée : MySQL inconnu (une autre table peut la référencer, MySQL refuse alors l'instantané), MariaDB instantané. Valeur par défaut expression (`uuid()`, `current_date`…) ou colonne auto-incrémentée : inconnu. PostgreSQL : `instant` = fichier de la table inchangé et aucun parcours (ajout de colonne sans défaut ou avec défaut constant/stable, retrait, renommage, défaut, DROP NOT NULL, VARCHAR élargi ou vers TEXT, retrait d'index ou de clé étrangère), `inplace` = pas de réécriture mais verrou bloquant les écritures (SET NOT NULL = parcours, CREATE INDEX, clé étrangère ajoutée), `rewrite` = nouveau fichier (entier élargi/réduit ou entier vers texte, défaut volatil comme `gen_random_uuid()`) ; clé primaire et le reste = inconnu. Limites connues : « probable » (la limite de 64 versions de lignes d'INSTANT de MySQL, un ROW_FORMAT=COMPRESSED ou un index FULLTEXT peuvent faire retomber sur une reconstruction, non lus) ; un « en place » peut reconstruire la table (`copiesTable` nul pour lui) ; `foreign_key_checks` supposé à sa valeur par défaut. Front : `utils/alterAlgorithm` (pastille `data-test="algorithm"` + phrase, `copyWarning`) ; AVANT « Valider », avertissement `data-test="copy-warning"` pour une copie/réécriture au-delà de 100 000 lignes estimées (`bigTable.estimatedRows`, donc l'estimation de `BigTablePolicy`) ou 100 Mo, ou dès que la politique d'installation juge la table volumineuse ; il cite les outils externes de changement de schéma en ligne sans jamais en lancer. Pas encore : PostgreSQL 14 à 17 (non vérifiés, donc inconnu), clé primaire PostgreSQL, autres formes d'ENUM/SET. Grosse table (#46) : `BigTablePolicy` (seuils par installation `TERRILDB_BIG_TABLE_WARN_ROWS` 100000 / `TERRILDB_BIG_TABLE_CONFIRM_ROWS` 1000000, 0 = désactivé, lignes ESTIMÉES de `TableDefinition`, jamais un COUNT) donne à `preview` un `bigTable` (`level` `none|warning|confirm_name`, `estimatedRows` nul = inconnu donc sans avertissement mais l'interface le dit, seuils) ; au niveau `confirm_name`, `apply` exige `confirmedTableName` égal au nom (sinon 409 `confirmation_required`, `reason: big_table_name`, vérifié avant la confirmation destructive) ; rien si le plan est vide ; modification et suppression de table, pas les UPDATE/DELETE massifs. Seules les tables sont éditables (pas les vues), pas Redis.
Front : `TableEditor` (colonnes, index, clés étrangères modifiables sur place ; brouillon `utils/structureDraft` où colonnes, clé primaire, index et clés étrangères se réfèrent par identifiant donc un renommage les suit ; lignes nouvelle / modifiée / retirée surlignées ; barre collante en haut avec le SQL calculé par `preview`, boutons Valider / Annuler, confirmation qui liste ce qui sera perdu ; « Supprimer la table » avec le SQL montré), seulement pour les tables (une vue reste en lecture seule), la section Index est un tableau façon phpMyAdmin (une ligne par colonne avec son rang, nom / type / unique en cellules fusionnées, monter, descendre, ôter, ajouter une colonne ; la clé primaire en est la première ligne, la clé de tri ClickHouse une ligne verrouillée) ; le menu « Vues de la connexion » garde une entrée « Structure » vers la dernière table ouverte (base et schéma compris) ; `TablePane` rafraîchit les listes de tables et l'arbre après application. Tailles : `IndexDefinition::$sizeBytes` et `TableDefinition::$dataBytes/$indexBytes` (octets sur disque, nuls si le moteur ne les donne pas ; HORS de l'empreinte, ils bougent sans que la structure change) : PostgreSQL `pg_relation_size` / `pg_table_size` / `pg_indexes_size` ; MySQL/MariaDB `information_schema.TABLES` pour les totaux et `mysql.innodb_index_stats` pour les index secondaires (lecture facultative, la clé primaire InnoDB est la table : pas de taille propre) ; ClickHouse `system.parts` (`bytes_on_disk`, `primary_key_size`) et `system.data_skipping_indices`. Le front montre une colonne « Taille » des index et « Données / Index / Total » sous le titre de la table. Fidélité (#85) : ce que le modèle ne sait pas redire ne se perd jamais en silence. ## Partitions, en lecture (src/Core/Schema/Partitioning*, Driver/*/…PartitionReader, issue #85)

`TableDefinition::$partitioning` (`PartitioningInfo` : méthode RANGE/LIST/HASH/KEY, expression, sous-méthode et sous-expression MySQL/MariaDB, liste de `PartitionDefinition` : nom, `bound` affichable, `upperBound` = limite haute EXCLUE d'une plage en littéral sans guillemets, `catchAll` = MAXVALUE/DEFAULT, lignes estimées, octets, sous-partitions) est HORS de l'empreinte de structure (les mesures bougent sans que la structure change : un test d'intégration le vérifie sur chaque moteur). Lecture seule : aucune édition de partitions. `MySqlPartitionReader` (`information_schema.PARTITIONS`, variantes COLUMNS/LINEAR rangées dans leur famille, taille = données + index, KEY() sans colonne = expression `PartitioningInfo::PRIMARY_KEY`) ; `PostgreSqlPartitionReader` (`pg_partitioned_table` + `pg_get_partkeydef`, `pg_inherits` (200 partitions au plus : `PostgreSqlPartitionReader::MAX_PARTITIONS` ; au-delà `PartitioningInfo::$totalCount` porte le nombre réel, `count()` le rend, `isTruncated()`, les totaux lignes/octets deviennent inconnus, l'audit ne juge plus l'échéance d'une plage coupée mais compte toujours les partitions ; `partitionCount` et `truncated` dans la réponse) + `pg_get_expr`, taille `pg_total_relation_size`, estimation -1 = nulle ; un sous-partitionnement PostgreSQL (partition elle-même partitionnée) n'est pas suivi). Exposé par `SchemaPresenter` (clé `partitioning`, nulle sans partition) ; front : `PartitionsSection` sous la structure (texte par interpolation, jamais v-html). Audit (`PartitionAuditor`, appelé par `SchemaAuditor`, qui prend un `$now` facultatif) : `partition_range_exhausted` (plage sur UNE colonne de date nue, aucune partition fourre-tout, dernière borne passée de plus d'un jour ; dans le doute (expression, borne illisible) on se tait ; suggestion = partition MAXVALUE / DEFAULT, nom cité refusé s'il contient un contrôle ou un séparateur de ligne) et `too_many_partitions` (au-delà de 1000, seuil de TerrilDB). Refus (`PartitionedTableGuard`, appelé par `SchemaChangePlanner::plan` après le diff, avant tout envoi) : retirer/renommer/changer le type d'une colonne de partitionnement, clé primaire ou unique du brouillon sans TOUTES les colonnes de partitionnement, clé étrangère ajoutée sur MySQL/MariaDB ; `UnsupportedPartitionChangeException` -> 422 `unsupported_partition_change` (`reason`, `subject`). Tests : `tests/Integration/Driver/{MySql,PostgreSql}PartitionsTest` (tables jetables supprimées en tearDown), `tests/Core/Optimizer/PartitionAuditTest`, `tests/Core/Schema/Change/PartitionedTableGuardTest`.

## Export (src/Core/Export, ExportController)

`CsvExporter` (RFC 4180, CRLF, UTF-8, BOM optionnel) et `JsonExporter` (tableau d'objets, colonnes dupliquées suffixées).
Le CSV neutralise les cellules qu'un tableur lirait comme une formule (`=`, `+`, `-`, `@`, tab, CR en tête) par une
apostrophe, sauf les nombres. `POST /web/connections/{id}/export` : lecture seule, mêmes garde-fous et même audit qu'une
exécution (`purpose: export`), 10 000 lignes par défaut, 100 000 au plus, en-tête `X-TerrilDB-Truncated` si coupé.

## Édition de données (src/Core/Data, TableDataController)

Même schéma que la structure : le client envoie des LIGNES (`updates` = valeurs d'origine + colonnes changées, `inserts` = valeurs,
`deletes` = valeurs d'origine), jamais du SQL. `DataChangePlanner` écrit les instructions du moteur avec des paramètres liés (`?`,
ou `{pN:Type}` pour ClickHouse) ; le texte montré (`display`) a les valeurs en clair mais n'est jamais exécuté. Une ligne se retrouve
par sa clé primaire PLUS les valeurs d'origine des colonnes modifiées (une ligne changée entre-temps n'est plus retrouvée) ; sans clé
(ClickHouse n'en a pas), par toutes ses colonnes comparables (JSON, binaire, tableaux exclus). Une valeur remise telle qu'elle était n'est
pas un changement (pour une colonne numérique, « 5.00 », « 5.0 » et « +5 » sont la même valeur, comparée en texte sans passer par un
flottant) ; si le moteur range la même valeur sous une autre écriture (MySQL annonce 0 ligne touchée), la ligne est recomptée dans la
transaction avant de parler de conflit. 500 changements au plus. `DataChangeService::preview` compte les lignes que chaque WHERE retrouve (il en faut
exactement UNE : sinon `ok: false`) ; `apply` refuse (409 `data_changed`) si ce n'est plus le cas, demande confirmation pour toute
suppression (409 `confirmation_required`, `reason: delete_rows`) puis exécute. PostgreSQL / MySQL / MariaDB : une transaction
(`DbalDataExecutor`), une modification ou suppression qui ne touche pas exactement une ligne annule tout. ClickHouse : pas de transaction,
instruction par instruction, et modifications / suppressions sont des MUTATIONS asynchrones (`ALTER TABLE … UPDATE/DELETE`) : elles ne se
voient pas tout de suite (`asynchronous: true`, l'interface le dit) ; un ajout est immédiat. Avertissements de l'aperçu (`warnings`, `DataWarning` : code stable + valeur, JAMAIS un blocage) : `not_transactional` (moteur de stockage MySQL/MariaDB sans annulation : MyISAM, MEMORY, ARCHIVE, CSV… ; `TableDefinition::$storageEngine/$transactional` lus dans `information_schema.TABLES.ENGINE` + `ENGINES.TRANSACTIONS`, hors empreinte ; le front retire alors la promesse « tout ou rien ») et `triggers` (nombre de déclencheurs : `information_schema.TRIGGERS`, `pg_trigger` non internes ; `TableDefinition::$triggerCount`). Ni refus par moteur, ni délai de verrou court, ni niveau READ COMMITTED : laissés à l'issue #74. Routes web seulement :
`POST /web/connections/{id}/tables/{name}/data/preview` et `.../apply` (ni API à jetons, ni MCP). Audit : `data.changed` (nombre de
modifications / ajouts / suppressions, colonnes touchées, SQL AVEC ses paramètres mais jamais les valeurs : une colonne secrète ne se
retrouve pas recopiée dans le journal) et `data.failed` (`row_changed` ou `engine_refused`, sans le message du moteur qui peut citer la valeur). Erreurs : 422 `invalid_data_change`, 409 `data_changed`,
409 `data_change_failed` (message du moteur). Front : vue « Données » (`TableDataPane`, route `data/:name`) = SQL modifiable + `DataGrid` ;
un onglet de requête par table (`QueryTab::table`), grille éditable seulement si la requête renvoie les colonnes de la table telles quelles
(clé primaire sélectionnée, ou toutes les colonnes sans clé) ET si l'instruction exécutée est une lecture simple de cette table (`isPlainReadOf` : SELECT … FROM table [alias] avec WHERE / ORDER BY / LIMIT, sans jointure, agrégat, DISTINCT, UNION ni sous-requête ; `QueryTab::lastSql` = ce dont le résultat est la réponse) ; brouillon `utils/dataDraft` ; bandeau « N changements en attente » avec
Vérifier (aperçu SQL) puis Appliquer ; relecture après application ; relancer la requête est bloqué tant que des changements attendent.
Tests : `tests/Core/Data`, `tests/Integration/Driver/DataChangeTest` (4 moteurs), `tests/Integration/Web/TableDataWebTest`.
