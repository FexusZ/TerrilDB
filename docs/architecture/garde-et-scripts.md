## Exécution et garde-fous (src/Core/Guard, src/Core/Query, src/Driver/*/…QueryRunner)

`QueryService` est le point d'entrée unique (web, API, MCP) : `StatementGuard` examine, `QueryRunner` du moteur exécute.
Le garde (lexical, `SqlScanner` par dialecte) n'accepte qu'UNE instruction, refuse les constructs hors transaction
(INTO OUTFILE, FOR UPDATE, fonctions de fichiers, LOAD/COPY, SET/BEGIN/COMMIT…) et demande confirmation pour ce qui
détruit (UPDATE/DELETE sans WHERE de même niveau, DROP, TRUNCATE, ALTER, GRANT, CALL). Un refus est définitif, aucune
confirmation ne le lève. Un identifiant entre guillemets ou backticks suivi de `(` (commentaires et espaces permis entre les deux, nom qualifié compris) est un APPEL : son nom déquoté, en majuscules, est comparé aux listes de fonctions refusées (`ScannedStatement::calledNames()`), sans devenir un mot du garde (une colonne `"sleep"` reste lisible). `QueryMode::ReadOnly` par défaut ; l'API et le MCP ne passent en lecture-écriture que par `ApiTokenAccess::writeOptions` (jeton avec droit d'écriture, `QueryOptions::$writes` = `WritePermissions` données/structure, refus définitif `write_not_permitted` du garde, avant toute confirmation ; CALL/DO exigent le droit structure). Le garde juge CHAQUE niveau : un WITH prend la nature de son instruction de tête (`ScannedStatement::withHead`, WITH … DROP = structure), une expression de table qui écrit (PostgreSQL `WITH d AS (DELETE …) SELECT …`) est une écriture, et un UPDATE/DELETE sans WHERE DANS SA PROPRE paire de parenthèses (`hasUnboundedRowChange`, y compris MERGE … THEN DELETE) demande confirmation ; `replace(…)`/`insert(…)` appelés ne sont pas des verbes (`isCallAt`), `FOR UPDATE`, `ON DUPLICATE KEY UPDATE`, `DO UPDATE` non plus. Refus définitif, dans les DEUX modes : fichiers/contrôle du serveur (`DANGEROUS_FUNCTIONS`) et verrous durables (`GET_LOCK`, `pg_advisory_*` : le moteur ne les refuse pas en lecture seule, le filtre est seul) ; `nextval`/`setval` = écriture (même derrière WITH ou EXPLAIN ANALYZE) ; pauses (`SLEEP`, `pg_sleep`, `BENCHMARK`) permises, coupées par le délai du moteur. OPTIMIZE/ANALYZE/VACUUM/REINDEX/CLUSTER et `CREATE OR REPLACE` demandent confirmation. Ce que le moteur EXÉCUTE se juge, pas l'enveloppe (`ScannedStatement::executedVerb`) : `EXPLAIN ANALYZE <instruction>` / `EXPLAIN (ANALYZE …)` = l'instruction expliquée (CREATE = structure, droit `writeSchema`, DELETE = données…), `ANALYZE <écriture>` (MariaDB) idem, `ANALYZE TABLE` reste une maintenance, un EXPLAIN ANALYZE dont l'instruction n'est pas un verbe connu (EXECUTE, DECLARE…) est refusé (`unsupported_statement`) ; PostgreSQL `SELECT … INTO <table>` (aussi derrière WITH ou EXPLAIN ANALYZE) CRÉE une table : structure + confirmation en lecture-écriture, `forbidden_construct` en lecture seule. `WHERE 1 = 1` et les tautologies ne sont PAS détectées (impossible en lexical : le moteur et les droits du compte restent les remparts). Autres refus définitifs prouvés contre les vrais moteurs (lot 2 de l'issue #87) : PostgreSQL, fonctions qui changent l'état du serveur alors que le moteur les joue en lecture seule (slots et origines de réplication, `pg_switch_wal`, `pg_create_restore_point`, sauvegarde, `pg_stat_reset*`, `pg_ls_*`…, `SERVER_STATE_FUNCTIONS`) ; `pg_notify` (effet de bord visible des autres sessions) et `query_to_xml*` (exécute le texte reçu : le filtre n'y verrait qu'un SELECT ; `table_to_xml`, qui lit une table nommée, reste permis) ; MySQL, indices `/*+ … */` lus comme du code, `MAX_EXECUTION_TIME` et `SET_VAR` refusés (ils levaient le délai du moteur) ; MariaDB, `NEXT VALUE FOR` = écriture ; ClickHouse, fonctions de table de fichiers et de lacs de données (`filesystem`, `iceberg*`, `deltaLake*`, `paimon*`, `hudi*`, `hive`…) que le moteur ne bloque pas hors `readonly=1` ; Redis, `COPY … DB` (autre base). Corpus de référence : `tests/Core/Guard/StatementGuardCorpusTest` (une ligne = instruction, moteur, mode, verdict) et `tests/Integration/Driver/GuardEngineConcordanceTest`. Le filtre peut se
tromper : le moteur fait foi. PostgreSQL : `BEGIN READ ONLY` + `statement_timeout` local + curseur serveur (limite de
lignes). MySQL/MariaDB : `SET SESSION TRANSACTION READ ONLY` (et non `START TRANSACTION READ ONLY`, qui laisse passer
le DDL), `MAX_EXECUTION_TIME` / `max_statement_time`, lecture non tamponnée, instructions multiples désactivées. Une
lecture est toujours annulée ; une écriture est validée si tout réussit. Limites connues : MySQL n'a pas de délai moteur
pour une écriture (MariaDB en a un : `max_statement_time` coupe aussi les écritures, qui sont alors annulées, mesuré) ; un DDL MySQL en lecture-écriture valide implicitement ; l'opérateur `?` de jsonb ne passe pas dans
EXPLAIN/SHOW sur PostgreSQL (il passe dans les SELECT). Vitess (`ServerFlavour::Vitess`, version lue une fois à l'ouverture par `MySqlDriver`) ne transmet pas `SET SESSION MAX_EXECUTION_TIME` : le délai passe par la directive `/*vt+ QUERY_TIMEOUT_MS=n */` (`VitessTimeout`, après SELECT/INSERT/UPDATE/DELETE/REPLACE, écritures comprises ; sans effet sur SHOW/WITH), erreur 3024 = `query_timeout` ; seul le délai en dépend, la lecture seule non. Cible `target-vitess` hors CI (`docs/vitess-tests.md`).

Verrous : `LockConflict` (Core/Driver, `fromEngineError(Engine, sqlState, code)`, codes du moteur seulement : MySQL/MariaDB 1213 = `deadlock`, 1205 = `lock_timeout` ; PostgreSQL 40P01 = `deadlock`, 40001 = `serialization_failure` (réessayable, code propre : ce n'est pas un interblocage), 55P03 = `lock_timeout` ; 57014 et 3024 restent `query_timeout`) ; les runners lèvent `LockConflictException`, `DbalDataExecutor` / `DbalDdlExecutor` posent `lock` sur `DataChangeFailedException` / `SchemaChangeFailedException` (`EngineLockConflict` lit PDO). `ErrorMapper` : 409 `deadlock` / `serialization_failure` / `lock_timeout` avec `retryable` (vrai SEULEMENT si `applied` est vide : un DDL MySQL/MariaDB/ClickHouse joué instruction par instruction qui a déjà appliqué quelque chose répond `retryable: false`, et le front dit de ne pas rejouer), sans message du moteur (il peut citer une valeur), `applied` et `failed` conservés ; `data_change_failed` / `schema_change_failed` portent `retryable: false` ; TerrilDB ne rejoue jamais seul ; journal `query.failed` avec `reason` = le code. Tests : `tests/Integration/Driver/LockConflictTest` (vrais verrous et vrai interblocage, pair en sous-processus `lock_peer.php`).

Erreurs courantes du moteur (#73, `EngineFault` dans Core/Driver, `EngineFaultReader` dans Driver) : **derrière `TERRILDB_DETAILED_ERRORS` (faux par défaut, `DetailedErrors`, lu par `ErrorMapper` et les trois journaux `AuditedQueries` / `AuditedDataChanges` / `AuditedSchemaChanges`, choix de l'installation pour tous ses membres : un refus précis d'un serveur prouve qu'il est joignable, donc cartographie le réseau interne) ; sans lui `ErrorMapper::withoutDetail` ramène chaque erreur au contrat d'origine (`target_unreachable`, `query_failed` avec le texte du moteur gardé dans `EngineFaultException::$engineMessage`, `data_change_failed`, `schema_change_failed`, audit `engine_error`) ; tout ce qui suit décrit le mode activé** ; même mécanisme que `LockConflict`, classé d'après le CODE du moteur seulement, jamais montré (le message peut citer une valeur, un hôte, un compte). Codes stables : `too_many_connections` (MySQL/MariaDB 1040, 1203, 1226 ; PostgreSQL 53300 ; 503, `retryable: true`, `retryAfter: 5` + en-tête `Retry-After`), `engine_permission_denied` (1044/1142/1143/1227/1370 ; 42501 ; 403, DISTINCT du 403 `permission_denied` des jetons : ici c'est le compte de la base cible qui est refusé), `duplicate_key` (1062 ; 23505 ; 409), `auth_failed` (1045 ; 28P01 ; 502, identifiants de la cible refusés), `auth_requires_tls` (3159 `require_secure_transport` ; PostgreSQL « no pg_hba.conf entry … no encryption » ; 502). Tous `retryable: false` sauf `too_many_connections` (et, sur une modification de structure jouée instruction par instruction, `retryable` retombe à faux dès que `applied` n'est pas vide). Lieux : `MySqlQueryRunner` / `PostgreSqlQueryRunner` lèvent `EngineFaultException` (console, API, MCP : même `ErrorMapper`) ; `DataChangeFailedException::$fault` et `SchemaChangeFailedException::$fault` (réponse du même code avec `applied` / `failed`, sans `message`) ; à l'OUVERTURE `TargetConnectionFailedException::$fault` (`DbalConnector`, `EngineFault::fromConnectionError`) rend ces codes à la place du générique `target_unreachable` (essai de connexion, ouverture par le web, l'API, le MCP). Mesuré : à la connexion libpq range TOUT refus PostgreSQL sous le SQLSTATE 08006 (le code ne dit rien), le TEXTE sert donc à CLASSER à cet endroit seulement (mot de passe, serveur plein, TLS, CONNECT refusé) ; MySQL et MariaDB (11.8 et 13) rendent leurs codes (3159 aussi sur MariaDB). Le reste (hôte injoignable, base inconnue, 1040 sur les autres moteurs) garde `target_unreachable` / `query_failed`. Audit : `reason` = le code stable (`query.failed`, `data.failed`, `schema.failed`), jamais le texte ; `schema.failed` n'écrit plus `error` (message du moteur) quand l'erreur est classée. Hors périmètre : ClickHouse et Redis (pas de classement), les instructions d'un script (leur erreur reste dans le compte rendu `ScriptResult`), les conseils pour d'autres codes. Tests : `tests/Core/Driver/EngineFaultTest` (toutes les combinaisons, messages réels mesurés), `tests/Integration/Driver/EngineFaultsTest` (vrai doublon, vrai compte jetable sans droit, limite de connexions du compte ; 1040 se prouve en unitaire seulement : le provoquer exigerait de saturer un serveur partagé), `AuditedEngineFaultTest`, web/API.

## Scripts SQL (src/Core/Query/Script, ScriptController, #47)

`ScriptAnalyzer` (découpage + verdict par instruction) est complété par `ScriptService` : `preview` (rien ne part, verdicts + `ScriptCapabilities`) et `execute` (tout est jugé AVANT la première exécution : un refus ou un droit d'écriture manquant d'UNE instruction = `ScriptRefusedException`, script entier arrêté ; une SEULE confirmation couvre les destructrices ; script vide = refus). Un `ScriptExecutor` par moteur (`TargetConnection::script()`, 501 ailleurs, Redis non concerné) : arrêt à la première erreur (l'erreur est dans le compte rendu `ScriptResult`, pas une exception), délai GLOBAL réparti (chaque instruction reçoit ce qui reste ; défaut 100 s, sous les 120 s du proxy de production), lecture bornée à 1000 lignes par instruction (`truncated` ; PostgreSQL passe par un curseur serveur : libpq tamponne sinon tout le résultat), instruction par instruction `applied` / `rolled_back` / `failed` / `not_run`, statut `committed` / `dry_run` / `rolled_back` / `partial` / `failed`. PostgreSQL : une transaction, DDL compris, tout ou rien. MySQL/MariaDB : une transaction, mais un DDL (et CALL/DO, par prudence) valide tout ce qui précède puis lui-même (`ScriptStatement::commitsImplicitly`, la transaction est rouverte après) : l'aperçu avertit (`mixed_data_and_ddl`, `ddl_not_transactional`) et `atomic` est faux. Une écriture dans une table SANS transaction (MyISAM, MEMORY, Aria… : `ScriptExecutor::nonTransactionalTables`, lues dans `information_schema`, repérées par nom dans le texte de l'instruction, `ScriptStatement::writesNonTransactional`) ne s'annule pas : `atomic` faux, avertissement `non_transactional_tables`, jeu à blanc refusé (`reason` du même nom), et après une erreur l'étape est rapportée `applied` (statut `partial`, jamais un faux `rolled_back`) ; limite : une table touchée par déclencheur, vue ou clé étrangère en cascade n'est pas vue. ClickHouse : pas de transaction, `partial` si une instruction échoue après d'autres. Jeu à blanc (`dryRun`, « Tester sans valider ») : exécution réelle puis ROLLBACK, seulement PostgreSQL et MySQL/MariaDB pour un script de données (sinon 409 `dry_run_unavailable` avec `reason` `no_transaction` / `implicit_commit`) ; réserves : verrous le temps du test, compteurs automatiques (séquences, auto-incréments) qui avancent. Routes web `POST /web/connections/{id}/script/preview` et `.../execute` (`script`, `confirmed`, `dryRun`, `timeoutMs`, `database`, `schema`) : réponse 200 avec le compte rendu même si une instruction échoue ; 403 `script_refused` (`reason`, `statement`), 409 `confirmation_required` (`reason: destructive_script`), 422 `invalid_script` / `script_too_large` (500 instructions, 1 Mo). Audit (`AuditedScripts`) : une ligne `query.executed` / `query.failed` par instruction ENVOYÉE (pas de ligne pour une instruction jamais partie), `executionId` commun, `rank`/`total` (« 3 sur 12 »), `script: true`, `status`, et pour l'échec le seul code (`sqlstate`, jamais le texte du moteur qui peut citer une valeur) ; un refus = une ligne `query.refused` sur l'instruction fautive ; une exception de l'exécuteur hors du moteur = une ligne `query.failed` (`reason: executor_error`). `DELIMITER` (commande du client mysql, pas du moteur) est REFUSÉE, jamais interprétée : `ScriptSplitter` (dialecte MySQL/MariaDB seulement) blanchit chaînes et commentaires puis refuse une ligne qui commence par `DELIMITER` suivi d'un argument, `UnsplittableScriptException::$reason = delimiter_directive`, 422 `invalid_script` avec `reason` (web, API, MCP ; un faux positif rare coûte un refus clair, jamais un découpage faux) ; un corps de procédure ou de déclencheur s'envoie comme UNE instruction en console, sans DELIMITER. Import de fichier (front, `utils/sqlFile.readSqlFile`, bouton « Importer un fichier .sql » de `ScriptPanel`) : lu dans le navigateur seulement, 1 000 000 octets au plus (même plafond que le serveur), octet nul = binaire refusé, UTF-8 strict (BOM retiré), vide refusé ; le texte va dans l'éditeur (confirmation avant de remplacer un texte existant), RIEN ne part avant l'aperçu serveur, donc la limite de 500 instructions n'est dite que par ce dernier (`script_too_large`) ; le compte rendu montre lignes affectées / lues et durée par instruction. Front : `ScriptPanel` (bouton « Script » de la console, texte de l'éditeur). API à jetons et MCP : `POST /api/v1/connections/{id}/script/prepare|execute`, outils `prepare_script` / `execute_script` (jetons qui écrivent), même cœur ; `WriteApproval::prepareScript|authorizeScript` : chaque instruction jugée avec les droits du jeton, UN jeton de confirmation (`ConfirmationKind::Script`) lié au texte exact, TOUJOURS exigé (même `singleStep`), `confirmed` pour le destructif.

Vitess (#39) : vtgate accepte `SET SESSION TRANSACTION READ ONLY` sans le transmettre, donc sur le PRIMAIRE la lecture seule du runner MySQL n'imposait rien (INSERT/UPDATE/DELETE passaient, y compris pour un jeton d'API ou MCP en lecture seule). `MySqlQueryRunner` ouvre donc TOUJOURS `START TRANSACTION READ ONLY` en lecture seule (en plus du SET de session, qui fait refuser le DDL ailleurs ; aucune détection de Vitess, qu'une version renommée ou illisible aurait laissé passer en ouvert) : le tablet refuse les écritures de DONNÉES. Un DDL s'exécute quand même hors de la transaction : sur le primaire Vitess le garde lexical est la SEULE barrière du DDL (un réplica `@replica` refuse tout). Transaction coupée à 30 s par le serveur. Bases = keyspaces (#40) : `MySqlIntrospector` reçoit `ServerFlavour::Vitess` de `MySqlDriver` (version lue UNE fois à l'ouverture) ; sur Vitess `listDatabases()` lit `SHOW DATABASES` (les keyspaces et les bases système) et jamais `information_schema.SCHEMATA`, qu'un vtgate route vers UN tablet : elle rend `_vt` et `vt_<keyspace>_<partition>` (ouvrir l'une d'elles échoue, `target_unreachable`) et cache les autres keyspaces (mesuré sur `target-vitess`, `8.0.35-Vitess`). `MySqlIntrospector::isVitessInternal` écarte `_vt` et `vt_<keyspace>_0` / `vt_<keyspace>_<plage>` par prudence ; un keyspace qui commence seulement par `vt_` reste listé. MySQL et MariaDB ne changent pas. Test : `tests/Integration/Driver/VitessKeyspacesTest` (cible `target-vitess`, sautée si éteinte).

Progression et arrêt d'un script (#169, PR 2 sur 6) : `ScriptExecutor::execute(…, ?ScriptProgress $progress)` ; `ScriptProgress::shouldStop()` est demandé AVANT chaque instruction (vrai = arrêt propre, jamais l'interruption d'une instruction en cours, aucun KILL), `executed(ScriptStepResult)` après chaque instruction exécutée ou en échec (« appliquée » est PROVISOIRE tant que la transaction n'est pas validée : seul le compte rendu final tranche). Un arrêt demandé se traite comme une erreur : ce que le moteur peut annuler l'est (PostgreSQL, données MySQL/MariaDB), un DDL MySQL garde ce qu'il a validé (`partial`), ClickHouse n'annule rien (`partial`) ; cause `failureReason = cancelled`, les instructions restantes `not_run`. `ScriptOptions::$progress` le transmet depuis `ScriptService`. Sans observateur, rien ne change. Tests : `tests/Integration/Driver/ScriptExecutorTest` (observateur `RecordingScriptProgress`, six moteurs).

Suivi des exécutions de scripts (#169, PR 1 sur 5 : la table seule, rien ne l'utilise encore) : `ScriptRun` (table `script_run`, migration à la main) garde l'état d'une exécution détachée : `ScriptRunStatus` (`queued`, `running`, puis un état terminal : `committed`, `dry_run`, `rolled_back`, `partial`, `failed`, `cancelled`, ou `interrupted`, qu'AUCUN worker n'annonce : c'est l'état d'une exécution sans signe de vie), nombre d'instructions et d'instructions finies, `cancelRequested` (lu entre deux instructions, jamais de KILL), signe de vie (`heartbeatAt` ; `HEARTBEAT_TIMEOUT_SECONDS` = 30). JAMAIS le texte du script ni d'une instruction : une empreinte SHA-256 du texte et, par instruction, rang / état / lignes / durée / `sqlstate` à cinq caractères (le message du moteur peut citer une valeur, l'entité le refuse). L'entité garde ses transitions (`InvalidScriptRunException`). `ScriptRunRepository` : `findOwned` (une exécution d'autrui est indiscernable d'une inexistante), `interruptStale` (UNE instruction), `purgeOlderThan` (terminées seulement). `app:audit:purge` les traite avec la même durée que l'audit (`TERRILDB_AUDIT_RETENTION_DAYS`) : d'abord les périmées sont interrompues, puis les terminées trop vieilles sont effacées. Choix du propriétaire (issue #169) : worker dédié, identifiants transmis par un socket Unix (mémoire du worker seulement), battement de cœur, pas de KILL.

Exécuteur d'une exécution détachée (#169, PR 3 sur 6 : sans le canal ni les routes, rien ne l'appelle encore) : `App\ScriptRun\ScriptRunRequest` = le message du lancement vers le worker (exécution, identifiants DÉCHIFFRÉS de la cible avec adresse épinglée et schéma, script, droits d'écriture, confirmation, jeu à blanc, délai) ; en mémoire seulement, `fromJson` refuse sans citer ce qu'il a reçu, `__serialize` lève, `__debugInfo` masque, 2 Mo et 1 Mo de script au plus ; une connexion AVEC REBOND est refusée pour l'instant (le tunnel est porté par la requête web). `ScriptRunExecutor::run` joue une exécution `queued` (une exécution inconnue, déjà lancée ou terminée n'est jamais rejouée) : ouvre la cible par le driver sans clé d'utilisateur, exécute par `ScriptService` (même garde, mêmes exécuteurs), `ScriptRunProgress` écrit l'avancement dans `script_run` et lit la demande d'annulation à la BASE à chaque question (`ScriptRunRepository::isCancelRequested`, l'objet en mémoire ne la verrait pas ; `requestCancelOf` la pose en une instruction), chaque appel est un signe de vie ; à la fin `ScriptRunReport` remplace les « appliquée » provisoires par le rapport final (`ScriptRun::finish(statut, date, rapport)`), statut `cancelled` si la cause est `cancelled`. Cible injoignable, script refusé, droit manquant : l'exécution se termine `failed`, sans exception ; seule une panne imprévue remonte, après avoir terminé l'exécution. Délai global : 600 s au plus (`QueryOptions::MAX_TIMEOUT_MS`).

Canal et worker des exécutions détachées (#169, PR 4 sur 6 : toujours sans route, rien ne l'appelle encore côté web) : le worker est un conteneur à part (`script-worker` de `compose.prod.yaml`, même image que l'application, `app:script:worker`, uid 33, lecture seule, sans capacité, mêmes réseaux que l'application pour atteindre les cibles ; `script-init` pose le dossier `script-sockets` en 0700 ; `deploy.sh` le démarre APRÈS l'application et n'échoue jamais à cause de lui). Il écoute `TERRILDB_SCRIPT_SOCKET` (`/run/script-runs/worker.sock`, mode 0600) ; `ScriptRunDispatcher::dispatch` (côté requête) y envoie un message « signature, JSON » (`ScriptRunChannel` : HMAC-SHA-256 dont la clé est tirée de `APP_SECRET`, que l'application et le worker partagent ; le dossier 0700 est le premier verrou, la signature ferme le reste ; PAS de `SO_PEERCRED`, qui exigerait `ext-sockets`, absente de l'image) et attend `ok` / `busy` / `refused` (`ScriptWorkerBusyException`, `ScriptWorkerUnavailableException` : l'exécution n'a PAS démarré). `ScriptWorkerServer` ne joue jamais de script lui-même : chaque exécution a son processus (`ProcessChildSpawner`, `bin/console app:script:run-child`, message par l'ENTRÉE STANDARD, jamais en argument, jamais dans un fichier ni dans l'environnement), 4 à la fois par défaut (`--max-children`, 1 à 32), un client muet est lâché après 5 s, message de plus de 2 Mo refusé. Signe de vie : le worker écrit lui-même `heartbeat_at` des exécutions de ses processus toutes les 5 s (`ScriptRunRepository::beatAll`), parce qu'une longue instruction occupe le processus qui joue le script ; au démarrage il déclare interrompue toute exécution périmée. Un worker arrêté ou redémarré perd ses exécutions (les identifiants n'étaient qu'en mémoire) : elles sont déclarées interrompues au bout de 30 s, rien n'est relancé sans le mot de passe de l'utilisateur. Vérifié en réel (worker, processus enfant et base de test) : progression visible en base pendant un `pg_sleep`, puis `committed` avec le rapport final.

Routes web des exécutions détachées (#169, PR 5 sur 6 : web seulement, l'interface suit) : `POST /web/connections/{id}/script/run` (`script`, `confirmed`, `dryRun`, `timeoutMs` 100 ms à 600 s, 600 s par défaut : hors du délai du proxy, c'est le but ; `database`, `schema`) répond 202 `{run}` ; `GET /web/script-runs/{id}` ; `POST /web/script-runs/{id}/cancel` (demande d'arrêt ENTRE deux instructions, répétable ; 409 `run_finished` si terminée ; jamais de KILL). `ScriptRunStarter` : `TargetOpener::resolve` (mêmes paramètres déchiffrés et même règle d'adresses que l'ouverture, adresse épinglée, SANS ouvrir ; une connexion avec rebond = 501 `unsupported_operation`), `ScriptService::judge` (mêmes refus, une confirmation, jeu à blanc que `execute`, sans la lecture des tables sans transaction qui exige la cible : le worker la refait), message construit AVANT d'écrire quoi que ce soit, exécution `queued` + ligne d'audit `script.started` (`executionId` = id de l'exécution, nombre d'instructions, `dryRun`, `confirmed`, empreinte SHA-256 du texte, JAMAIS le texte ; elle existe même si le processus meurt en route), puis `ScriptRunLauncher::dispatch` (alias de `ScriptRunDispatcher` ; les tests des routes le remplacent par `RecordingScriptRunLauncher`, un worker dans un autre processus ne verrait pas la base du test). Worker occupé = 503 `script_worker_busy` (`Retry-After: 5`), worker absent = 503 `script_worker_unavailable` : l'exécution est alors terminée `failed`, jamais laissée en file. `ScriptRunAccess` : lecture et annulation cloisonnées par compte (404 pour l'exécution d'autrui, indiscernable d'une inexistante), les exécutions vivantes sans signe de vie sont déclarées interrompues À LA LECTURE, la ligne est relue à la base (le worker l'écrit depuis un autre processus). Les lignes d'audit des instructions s'écrivent depuis le processus du worker, au nom de celui qui a lancé (`ScriptRunRequest::$audit`), sous l'identifiant de l'exécution (`AuditedScripts::execute(…, $executionId)`), avec les statuts FINAUX. La réponse (`ScriptRunPresenter`) ne porte ni le texte du script ni celui d'une instruction.

Interface des exécutions détachées (#169, PR 6 sur 6 pour le web ; API à jetons et MCP : plus tard) : `ScriptPanel` a une case « En arrière-plan » (active après l'aperçu) qui change le bouton en « Lancer en arrière-plan » : `startScriptRun` (`POST …/script/run`, réponse immédiate), puis le panneau SUIT l'exécution toutes les 2 s (`fetchScriptRun`) tant qu'il est affiché et qu'elle n'est pas terminée ; le suivi ne porte jamais de texte, l'interface retrouve celui d'une instruction par son rang dans l'aperçu qu'elle vient de juger, avec le code SQLSTATE d'un échec (jamais un message du moteur). « Demander l'arrêt » (`cancelScriptRun`) le dit : l'arrêt se fait ENTRE deux instructions, celle qui tourne va à son terme, aucun KILL. Fins expliquées par `bgOutcome` : appliqué, test, tout annulé, partiel, arrêté à la demande, interrompu (worker sans signe de vie : « vérifiez l'état de la base avant de relancer »), impossible à jouer. Un suivi qui échoue 5 fois de suite s'arrête avec un message qui dit que le script, lui, continue sur le serveur ; modifier le texte oublie le suivi ; démonter le panneau arrête la scrutation. Pas encore : retrouver une exécution en quittant la page (liste des exécutions du compte), un compte rendu par instruction avec le texte conservé.

## Console du site : avertir plutôt que refuser

La console d'une personne connectée ne perd aucun outil (consigne du propriétaire : tout ce qu'un terminal SQL permet, au maximum un « attention »). `StatementGuard::check(…, lenient: true)` (`QueryOptions::$lenient`, posé par `QueryController` seulement) transforme les refus `forbidden_construct` (fichiers du serveur, `INTO OUTFILE`, `LOAD`/`COPY`, verrous durables, fonctions d'état PostgreSQL, indices de délai MySQL, clauses de verrou, fonctions de table ClickHouse sortantes) en demande de confirmation (409 `confirmation_required`, `reason: forbidden_construct`, texte d'avertissement côté interface). Le même jugement est rejoué SANS ces refus : tout autre refus reste un refus (une seule instruction, mode lecture seule, droits d'écriture, instruction illisible), donc `LOAD DATA` reste refusé en lecture seule. Les scripts de la console suivent la même règle (`ScriptOptions::$lenient`, aperçu, exécution et exécution détachée : le drapeau voyage dans le message du worker, `ScriptRunRequest::$lenient`, absent = strict) : une instruction hors cadre compte dans l'UNE confirmation du script (`destructive_script`) ; un refus restant (verbe inconnu comme `COMMIT`) arrête tout. Les jetons d'API, le MCP, l'export et le plan gardent le jugement strict. Le moteur et les droits du compte de la base cible restent les remparts. `REVERT` (migrations Vitess) est une modification de structure, avec confirmation.

Redis, même règle (`RedisCommandGuard::check(…, lenient: true)`) : une commande hors de la liste blanche (KEYS, CONFIG, CLIENT, scripts, commandes bloquantes ou de flux, FLUSHALL, `COPY … DB`, sous-commande non listée, commande que le garde ne connaît pas) demande confirmation (`forbidden_construct`). En lecture seule, le SERVEUR a le dernier mot : `RedisQueryRunner` interroge `COMMAND INFO` et refuse ce qu'il marque écriture, administration, bloquant ou publication, même confirmé ; en lecture-écriture la commande confirmée part telle quelle (avec le droit d'écrire). Restent refusées : plusieurs commandes, et le contrôle de session ou de transaction (SELECT, MULTI, EXEC, WATCH, QUIT… : chaque commande part sur un client neuf, ces commandes n'auraient aucun effet). Jetons d'API et MCP : liste blanche stricte, inchangée.
